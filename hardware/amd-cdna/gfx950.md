## 21. Target Architecture Reference (gfx950 / CDNA4 / MI350X / MI355X)

The optimization method is architecture-agnostic — every principle and
lever applies to any AMDGPU CDNA target. This section collects the
**gfx950 / CDNA4** specifics. When
porting to gfx942 (MI300X), gfx940 (MI250X-class CDNA3), or gfx90a,
the corresponding caps and intrinsics differ — always verify against
the vendor spec sheet.

### 21.1 MFMA Atom Catalog (gfx950)

On gfx950 the following are available:

| Atom | A / B / C dtype | M × N × K | Notes |
|---|---|---|---|
| `f16_4x4x4` | fp16 / fp16 / fp32 | 4×4×4 | Many independent small problems per wave (used by small-channel direct conv) |
| `f16_16x16x16` | fp16 / fp16 / fp32 | 16×16×16 | Standard small tile |
| `f16_16x16x32` | fp16 / fp16 / fp32 | 16×16×32 | K-packed (recommended over `16x16x16`) |
| `f16_32x32x8` | fp16 / fp16 / fp32 | 32×32×8 | Larger output tile |
| `f16_32x32x16` | fp16 / fp16 / fp32 | 32×32×16 | K-packed + larger output tile. **C-output lane layout matches A-input layout** — chained MFMA without re-pack |
| `bf16_16x16x16` | bf16 / bf16 / fp32 | 16×16×16 | |
| `bf16_16x16x32` | bf16 / bf16 / fp32 | 16×16×32 | K-packed |
| `bf16_32x32x16` | bf16 / bf16 / fp32 | 32×32×16 | K-packed; chained-MFMA layout match |
| `fp8_*_f8` | fp8e4m3 / fp8e4m3 / fp32 | varies | CDNA4 native fp8 MFMA |
| `bf8_*_bf8` | bf8e5m2 / bf8e5m2 / fp32 | varies | CDNA4 native bf8 MFMA |
| Mixed-precision MFMA | mixed | varies | bf16 / fp8, fp16 / fp8, etc. |
| Scaled MFMA (block-scale) | fp8 + per-block scale | varies | block-scale GEMM uses the fp8 atoms |
| MX (microscaling) MFMA | fp8 + E8M0 shared exponent | varies | MX GEMM with an E8M0 scale layout |
| i8 / i4 atoms | int8 / int4 packed | varies | i4 needs an unpack step |

Lane-layout matching across chained atoms: the 16×16 atoms'
C-output doesn't natively match their A-input, so a QK→PV-style
chain needs an LDS round-trip or a cross-lane permute. The 32×32
atoms natively match — prefer them when the chain pattern allows
(e.g. a 32×32 transposed-QK path in 2D attention).

### 21.1a Package memory (HBM) and physical hierarchy

On-chip storage is three distinct categories — registers (operands,
compiler-managed), LDS (software-managed scratchpad), and L1/L2
(hardware-managed caches) — backed by off-package HBM. Physical layout
and why they are not interchangeable: see
[memory-hierarchy](../../kernel-optimization/levers/memory-hierarchy.md).

| Resource | gfx950 MI350X | gfx950 MI355X | gfx942 MI300X |
|---|---|---|---|
| HBM type | HBM3E | HBM3E | HBM3 |
| HBM capacity | 288 GB | 288 GB | 192 GB |
| HBM bandwidth | ~8 TB/s | ~8 TB/s | ~5.3 TB/s |
| LDS per CU | 160 KB | 160 KB | 64 KB |
| VGPR + AGPR / SIMD (unified) | 512 | 512 | 512 |
| Max per wave | 256 VGPR + 256 AGPR | 256 VGPR + 256 AGPR | 256 VGPR + 256 AGPR |
| SGPR / CU | 800 | 800 | 800 |

MI350X and MI355X are the **same silicon**: they differ only in form
factor and power — MI350X is air-cooled (~1000 W TDP), MI355X is
liquid-cooled (~1400 W TDP, higher clocks → higher peak FLOPs). Memory
and register sizing are identical between them. The big gfx950-vs-gfx942
delta for kernel work is LDS (160 KB vs 64 KB/CU, 64 vs 32 banks),
which also flips the preferred swizzle (padding vs XOR).

### 21.2 LDS specifics

| Spec | gfx950 | gfx942 (MI300X) | gfx90a (MI250X) |
|---|---|---|---|
| LDS per CU | 160 KB | 64 KB | 64 KB |
| LDS banks | 64 | 32 | 32 |
| Preferred swizzle | padding | XOR | XOR |
| `ds_read_b64_tr_b16` / `ds_read_b128_tr_b16` | CDNA4 only | — | — |
| `ds_read_tr_b8` (i8 / fp8 / bf8 transposed) | CDNA4 only | — | — |
| `ds_read_b128` conflict period | 64 dwords | 32 dwords | 32 dwords |
| `ds_write_b128` conflict period | 32 dwords | 32 dwords | 32 dwords |
| Other `ds_read_b{32,64}` / `ds_write_*` conflict period | 32 dwords | 32 dwords | 32 dwords |
| Intra-dword sub-dword accesses | conflict-free | conflict-free | conflict-free |
| Unaligned `ds_read_u16` charged to | `SQ_LDS_IDX_ACTIVE` (not `SQ_LDS_BANK_CONFLICT`) | same | same |

Important asymmetry: `ds_write_b128` (32-dword period) and
`ds_read_b128` (64-dword period) on gfx950 can require **different
swizzle strategies** for reads vs writes. See `LDS_a.md` / `LDS_b.md`
in the empirical studies for the full opcode × phase table.

### 21.6 Buffer descriptor (AMDGPU)

| Spec | Value | Notes |
|---|---|---|
| DW3 flag for OOB-safe buffer-resource | `0x00027000` (= 159744) | TYPE=2 (BUFFER_RESOURCE), DATA_FORMAT=4 (32-bit dword), NUM_FORMAT=4 (UINT) |
| Building the descriptor | from base pointer + `num_bytes` | Must emit the correct DW3 — OOB lanes silently return zero |
| `raw_ptr_buffer_load_lds` dwords accepted | `{4, 3, 1}` only — **not 2** | Async tile loaders must pick the dword count accordingly |
| Async DRAM→LDS write contract | lane-contiguous addresses only | Arbitrary per-lane swizzled destinations corrupt output |
| `s_waitcnt` immediate `20336` (`0x4F70`) | vmcnt 16, expcnt 7, lgkmcnt 15 | lgkmcnt is 4 bits on gfx9 (max 15) |

### 21.7 FP8 / quantization (gfx950)

| dtype | Range | Mantissa bits | Native MFMA on gfx950 |
|---|---|---|---|
| `FP8E4M3` | ±240 (no Inf) | 3 | Yes |
| `BF8E5M2` | ±57344 (with Inf) | 2 | Yes |
| `I8` saturating | ±127 | int8 | Yes (i8 MFMA) |
| MX scale | E8M0 shared exponent | block-scaled | Yes (scaled MFMA) |
| Block-scale mantissa | FP8 or BF8 | block-scaled | Yes |
| Codebook (i4) | packed nibble pairs | int4 | unpack-then-MFMA |

Native fp8 MFMA can be enabled separately for the QK and PV products
in 2D attention; the working dtype (bf16) is preserved
for QK softmax math even when the MFMA itself is fp8.

### 21.8 Compiler caveats specific to gfx950

- **Scheduling barriers never reach the ISA**, on gfx950 or gfx942.
  `sched_barrier` / `sched_group_barrier` are directives to the LLVM
  machine scheduler and print only as `;` comments. A count of 0 in the
  final ISA is expected; judge their effect by the instruction order.
- **`-mllvm -enable-post-misched=0`** is safe in CK's CMake-generated
  code but has been observed miscompiling MLIR-generated kernels on
  this arch — treat as risky.
- The remaining recommended CK-style flag stack
  (`-mllvm -amdgpu-function-calls=false`,
  `-mllvm -amdgpu-early-inline-all=true`,
  `-mllvm --lsr-drop-solution=1`, `-fno-offload-uniform-block`,
  `-O3`, fast / unsafe math) has been measured safe but rarely
  moves the needle by more than 1 % on gfx950 — large gaps come
  from kernel structure, not flags.

### 21.9 Default ISA target

| Spec | Value |
|---|---|
| Default ISA target | `amdgcn-amd-amdhsa--gfx950` |
| LLVM datalayout | gfx950 datalayout string baked into lowering |
| Other supported targets | `gfx942` (MI300X), `gfx90a` (MI250X) — verify MFMA atom shapes are valid for the target |

To target a different arch, set the ISA triple (e.g.
`amdgcn-amd-amdhsa--gfx942`) and verify the atoms picked are valid
warp-tile shapes for that arch.

## Lessons from worked examples

- **gfx950 FP8 E4M3 tops out at ±448, not ±240.** gfx950 uses OCP FP8 (bias 7); ±240 is the CDNA3 FNUZ limit. Set quantization scales against 448, and never bit-copy FNUZ data in. Details: [low-precision-formats](low-precision-formats.md).
- **Transposing LDS reads are 64-bit or 96-bit only.** The CDNA4 ISA lists `ds_read_b64_tr_b4`, `ds_read_b64_tr_b8`, `ds_read_b64_tr_b16`, and `ds_read_b96_tr_b6`. There is no 128-bit transposing read; plan two b64 reads per 16 B.
- **Legacy MFMA shapes run at half the gfx950 peak.** `16x16x16` f16/bf16 and `16x16x32` fp8 keep their CDNA3 cycle counts. Use `16x16x32` f16/bf16, `16x16x64` i8, and the `f8f6f4` K=128 atom for FP8 to reach the doubled rate. Table: [matrix-core-generations](matrix-core-generations.md).
- **`sc0`/`sc1` are scope bits, not cache-bypass bits (gfx942 and gfx950).** On loads and stores: none = wave, `sc0` = workgroup, `sc1` = agent, both = system. A cross-workgroup poll with `sc0` alone can spin forever on a stale L1 line. ([LLVM AMDGPUUsage, GFX942 memory model](https://llvm.org/docs/AMDGPUUsage.html))
